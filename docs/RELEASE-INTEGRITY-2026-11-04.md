# Release integrity and save-boundary verification

Implementation work for AUD-01, AUD-02/T09, AUD-03 and source verification for ARCH-01/T07. No hosted deployment, production storage reset, SQL migration or production write probe was performed.

## Exact release bytes

`.gitattributes` now selects LF for text on every platform while retaining automatic binary detection. The browser bundler normalizes authored fragment line endings before concatenation. The offline builder canonicalizes the actual served JS/CSS/JSON/HTML/SVG bytes before calculating SHA-256, including older Windows checkouts created before the attributes existed. Binary assets are untouched. Its `--check` mode is read-only and rejects noncanonical bytes or a stale manifest.

The worker's strict SHA-256 verification and previous-complete-shell protections are unchanged. Leaflet CSS's reviewed inventory hash changes solely because its checked-in CRLF bytes become LF; the remaining vendored checksums and versions are unchanged. Do not generate a manifest and subsequently transform its assets, and do not hand-edit generated bundles.

Before packaging a static release, run:

```text
npm run build
npm run check:build
node scripts/check-vendor-integrity.cjs
node scripts/verify-release.cjs
```

`verify-release.cjs` checks every allowlisted local asset against the actual manifest. An optional public base URL instead reads its served worker and verifies every asset twice: bare URL and the exact `?shell=<release>` query used by the worker. It performs public GETs only and accepts no account credentials:

```text
node scripts/verify-release.cjs https://example.test/site/
```

Running that command against the newly published URL is still a deployment acceptance gate. Local success is not proof that the existing live deployment has changed.

## Save and owner boundary

Supplied `supabase-accounts.sql` enables owner RLS with matching `USING` and `WITH CHECK` predicates, closes anonymous access, and validates identity/shape/size/revision in the `SECURITY INVOKER` save RPC. However, authenticated direct own-row INSERT/UPDATE/DELETE grants permit bypass of RPC-only checks. Revoking those grants alone would break the invoker RPC. No SQL was changed under this implementation brief's prohibition on schema changes.

This was reproduced in **isolated in-memory PostgreSQL 18.6 / PGlite 0.5.15**, installed only as scratch tooling, never in Herald's package manifest. The fixture supplies an `auth.users` table and an `auth.uid()` stub reading synthetic claims. It executes the repository account schema and existing `tests/account-security.sql` unchanged:

- Existing SQL assertions pass: owner access, cross-owner denial, anonymous denial, stale RPC rejection, additive tracker/logo fields and unknown-field preservation.
- A valid fictional RPC save produces revision 1.
- The RPC rejects `{}` with SQLSTATE `22023`.
- The same owner directly updates payload to `{}` successfully and leaves revision at 1. Thus owner RLS alone does not enforce the save contract in this source schema.

This proves a source-contract integrity bypass, not deployed exposure or cross-account disclosure. PGlite's single connection does not establish concurrent row-lock behavior. No real Auth/JWT/session, deployed grants, production backup restoration, email delivery or project configuration was verified.

Before release, inspect deployed grants, owner policies and function definitions read-only, then reproduce with dedicated users in isolated Supabase staging. If the deployed bypass exists, design a compatible, explicitly scoped save boundary together with its privileges and test both old and new clients. Do not introduce a definer function merely to bypass a permission error, and do not execute the existing SQL fixture against the owner's live account.

Current [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) confirms that grants and row predicates are separate checks. The [Supabase changelog](https://supabase.com/changelog) was reviewed on 4 November 2026; no CLI or database upgrade was performed. The scratch PostgreSQL engine follows the [PGlite in-memory API](https://pglite.dev/docs/).
